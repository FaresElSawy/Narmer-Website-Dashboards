## Recommended B2C request sequence

1. Load public Categories and Products. For browse filters, use `GET /api/v1/b2c/products` and `/facets` with the same normalized state and `X-Language`. Filter by stable option keys, never translated labels. The list returns only active Products in visible category ancestry; zero-stock items remain browseable. `matchingPrice` and `matchingVariantId` are preview hints and must not be treated as cart selection or trusted price. [Products, lines 518–550](../../Backend%20Files/New%20Backend%20Files/modules/PRODUCTS_FRONTEND.md#L518)
2. Create/retain Cart selection using only `productId`, optional `variantId`, and absolute `quantity`. A guest must omit `Authorization`, use `credentials: include`, and let the browser hold the HttpOnly `narmer_cart_b2c` cookie. Login does not merge automatically; explicitly call merge after sign-in. [Cart, lines 29–38](../../Backend%20Files/New%20Backend%20Files/modules/CART_FRONTEND.md#L29), [lines 62–76](../../Backend%20Files/New%20Backend%20Files/modules/CART_FRONTEND.md#L62), [lines 247–268](../../Backend%20Files/New%20Backend%20Files/modules/CART_FRONTEND.md#L247)
3. Optionally preview a coupon with current Cart ownership and the same intended checkout phone. This is a read calculation: it neither stores the code nor reserves inventory or coupon capacity. Active Sale lines are ineligible; shipping is excluded from coupon minimum spend. [Coupons, lines 7–13](../../Backend%20Files/New%20Backend%20Files/modules/COUPONS_FRONTEND.md#L7), [lines 205–232](../../Backend%20Files/New%20Backend%20Files/modules/COUPONS_FRONTEND.md#L205)
4. POST checkout preview with explicit buyer contact/address, payment method and optional coupon code. It snapshots current Cart/product/Sale/coupon/shipping state for 24 hours but reserves no stock. An InstaPay preview provides account instructions and accepts one raw image proof upload; upload is not payment confirmation and is not safely repeatable after an uncertain response. [Orders, lines 44–52](../../Backend%20Files/New%20Backend%20Files/modules/ORDERS_FRONTEND.md#L44), [lines 223–244](../../Backend%20Files/New%20Backend%20Files/modules/ORDERS_FRONTEND.md#L223)
5. Place with the same `checkoutId`; include `proofId` for InstaPay and omit it for COD. Placement revalidates selection, current prices, shipping/coupon eligibility and stock, then atomically attaches proof, deducts stock, redeems coupon, creates Order and consumes Cart. On timeout, preserve and replay the exact body; same checkout/proof is idempotent, different proof conflicts. [Orders, lines 231–244](../../Backend%20Files/New%20Backend%20Files/modules/ORDERS_FRONTEND.md#L231)
6. For guest tracking, retain the opaque token from the first successful placement privately, use `X-Order-Token`, and honor its original 90-day expiry. Do not put it in query strings. Proof GETs return private `image/webp` bytes, not a public URL or JSON success envelope. [Orders, lines 54–103](../../Backend%20Files/New%20Backend%20Files/modules/ORDERS_FRONTEND.md#L54), [lines 557–561](../../Backend%20Files/New%20Backend%20Files/modules/ORDERS_FRONTEND.md#L557)

## Contract constraints that should shape implementation

- All money is integer EGP piastres; preserve `null` versus zero. `discountedPrice: 0` is a valid free price. Cart subtotal can be null when a line is unpriceable. Prices in Product, Cart, Coupon preview, and Checkout are current calculations, not price locks. [Products, lines 11–38](../../Backend%20Files/New%20Backend%20Files/modules/PRODUCTS_FRONTEND.md#L11), [Cart, lines 88–96](../../Backend%20Files/New%20Backend%20Files/modules/CART_FRONTEND.md#L88)
- Cart quantity is an absolute desired count (0 removes the exact `(productId,variantId)` pair); do not retry as a delta. Up to 100 distinct selections and 10,000 units per line. Server rejects changed/foreign variants and insufficient stock; it preserves prior Cart state on failure. [Cart, lines 40–60](../../Backend%20Files/New%20Backend%20Files/modules/CART_FRONTEND.md#L40)
- Guest Cart retention is 30 days, renewed on successful item writes, not ordinary reads. Expired selections are cleared, and logout does not delete the account Cart. The Cart cookie is HttpOnly and JavaScript must not read or construct it. [Cart, lines 62–86](../../Backend%20Files/New%20Backend%20Files/modules/CART_FRONTEND.md#L62)
- Retries differ by operation: absolute Cart PUT and Wishlist PUT/DELETE are safe for the same intent; Cart merge must reconcile both owners; checkout preview creates a new expiring record and should not loop; proof upload is not idempotent; placement is safe only with the exact same checkout/proof pair. Respect `Retry-After` on 429, retain form/state, and do not refresh a token to evade a limit. [Cart, lines 257–287](../../Backend%20Files/New%20Backend%20Files/modules/CART_FRONTEND.md#L257), [Orders, lines 618–619](../../Backend%20Files/New%20Backend%20Files/modules/ORDERS_FRONTEND.md#L618)
- Wishlist has no guest list, merge, selected variant, quantity, or price snapshot. It is account/locale scoped, 100 product IDs maximum, and returns hidden saved products as unavailable without leaking old catalog details. [Wishlist, lines 5–18](../../Backend%20Files/New%20Backend%20Files/modules/WISHLIST_FRONTEND.md#L5), [lines 244–260](../../Backend%20Files/New%20Backend%20Files/modules/WISHLIST_FRONTEND.md#L244)
- Sale activation is server-time based, half-open `[startsAt, endsAt)`, and replaces rather than stacks saved discounts. It changes public Product/Cart display pricing, not stored baseline prices. Coupons exclude any active Sale line, even if rounding produces no actual reduction. [Sales, lines 7–11](../../Backend%20Files/New%20Backend%20Files/modules/SALES_FRONTEND.md#L7), [lines 65–71](../../Backend%20Files/New%20Backend%20Files/modules/SALES_FRONTEND.md#L65), [Products, lines 34–38](../../Backend%20Files/New%20Backend%20Files/modules/PRODUCTS_FRONTEND.md#L34)
- Orders are immutable purchase snapshots. Product names/prices/categories may later change without rewriting history. `items[].category` is nullable for legacy rows and represents the historical direct category, not a parent roll-up. Only staff DTOs expose `quotedPreview`, user ID, proof ID and audit details; customer DTOs intentionally omit them. [Orders, lines 246–275](../../Backend%20Files/New%20Backend%20Files/modules/ORDERS_FRONTEND.md#L246), [lines 655–659](../../Backend%20Files/New%20Backend%20Files/modules/ORDERS_FRONTEND.md#L655)
- Staff status changes require latest `expectedStatus`; the permitted graph, stock restoration on cancel/return, and refund marker are separate from actual payment verification/refund execution. No customer cancellation or payment/refund API exists. [Orders, lines 563–579](../../Backend%20Files/New%20Backend%20Files/modules/ORDERS_FRONTEND.md#L563)
- Coupon per-person limits use the submitted checkout phone, not verified account identity. The secret-derived identity is not returned, but the contract explicitly says phone ownership is unverified. Do not imply identity verification in UI copy. [Coupons, lines 205–216](../../Backend%20Files/New%20Backend%20Files/modules/COUPONS_FRONTEND.md#L205)
- Product size charts are optional guide content on Product list/detail only; they do not define available variants or validate size. Cart/Wishlist/Orders do not carry chart data. Product writes have `sizeChartId`; public projections expose localized chart content only. [Products, lines 624–630](../../Backend%20Files/New%20Backend%20Files/modules/PRODUCTS_FRONTEND.md#L624), [Cart, lines 326–328](../../Backend%20Files/New%20Backend%20Files/modules/CART_FRONTEND.md#L326), [Wishlist, lines 309–311](../../Backend%20Files/New%20Backend%20Files/modules/WISHLIST_FRONTEND.md#L309)

## Implementation checks and settled boundaries

- **Price-range contract:** The documented UI input is an EGP amount converted to integer piastres for `minPrice`/`maxPrice`; the wire values are digit-only, bounded at 1,000,000,000, and inclusive. Implement that conversion as written. Add a focused request-boundary check for representative EGP values and the maximum before wiring the UI. The example uses `10000` and `30000` on the URL, which is consistent with piastres after conversion; no contract contradiction is evidenced. [Products, lines 524–550](../../Backend%20Files/New%20Backend%20Files/modules/PRODUCTS_FRONTEND.md#L524)
- **Catalog configuration check:** Facets recognize stable option keys exactly named `size` and `color`; translated labels do not qualify. Before implementing these controls, inspect current catalog data for those keys. Generic options remain supported but are not searchable as size/color. [Products, lines 526–533](../../Backend%20Files/New%20Backend%20Files/modules/PRODUCTS_FRONTEND.md#L526)
- **Design presentation:** New Orders adds historical `category` to quote/order item snapshots. It can be null for older records; display the agreed localized “Unknown category” fallback and do not reconstruct it from the current catalog. [Orders, lines 153–154](../../Backend%20Files/New%20Backend%20Files/modules/ORDERS_FRONTEND.md#L153), [lines 655–659](../../Backend%20Files/New%20Backend%20Files/modules/ORDERS_FRONTEND.md#L655)

The B2C-only commerce scope, guest and customer shopping paths, COD/InstaPay methods, and unknown-category fallback are treated as settled requirements for this handoff; this review does not reopen them.

## Suggested phased implementation plan for the next coding chat

1. Start with Products browse/detail and catalog API client: use the documented integer-piastre filters, wire facets with stale-response protection, and render list-only `matchingPrice` without treating it as cart authority.
2. Implement guest/customer Cart and explicit sign-in merge; verify HttpOnly cookie transport, absolute quantity mutation, unavailable/insufficient-stock rows, and account-scoped cache clearing.
3. Add checkout form and optional Coupon preview, then COD/InstaPay branching, private proof upload, exact placement replay recovery, and guest tracking. Keep order/proof responses out of shared caching.
4. Add signed-in Wishlist as a separate product-level feature; link to Product detail for variant choice and size guide, then Cart for purchase.
5. Add the approved staff Sales/Coupon/order screens with role-specific navigation and the server's authorization behavior. Keep status writes guarded by `expectedStatus`. Follow the main handoff's B2B-first phase ordering rather than treating this commerce-only slice order as the overall project plan.
6. After backend contracts and design decisions are approved, implement in small slices and verify representative guest, signed-in, Arabic/English, mobile, error, stale-state and expiry paths. **The new coding chat should present this phased plan and wait for explicit approval before changing application code.**
