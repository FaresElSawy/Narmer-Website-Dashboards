## B2B visitor journey

The B2B request flow is a service inquiry, not commerce checkout:

1. Fetch public Forms definitions and show only active types. The five stable types are `spinning`, `weaving`, `fabric`, `school-uniforms`, and `wholesale` (`modules/FORMS_FRONTEND.md:9-21, 27-35`). Startup creates all five unpublished with no configurable questions, so the public list starts empty until staff configure and publish forms (`FORMS_FRONTEND.md:19-21, 29`).
2. For `wholesale`, also fetch public Wholesale offers. For other service types, render the configured form fields. The selected definition's `type` and exact `version` must remain with the visitor's answers (`FORMS_FRONTEND.md:144-155, 251-259`; `LEADS_FRONTEND.md:252-262`).
3. Create a 24-hour draft for the selected type. Retain its `draftId` and one-time `draftToken` privately; the token is sent in `X-Lead-Draft-Token`. Optional images are uploaded as raw bytes to that draft, not via catalog Media (`LEADS_FRONTEND.md:21-27, 41-88`).
4. Submit contact, configurable answers, exact `formVersion`, optional draft image IDs, and for wholesale only, selected `offerId`/`version`/whole-pouch `quantity` rows (`LEADS_FRONTEND.md:90-142`). The service requires `name`, `phone`, `governorate`, and `district`; email is optional. A guest remains guest-owned even if their email matches an account; an authenticated B2B customer is associated only by their B2B bearer identity (`LEADS_FRONTEND.md:11-15, 100-117`).
5. Show the receipt immediately. A guest receives a tracking token good for 90 days; read with `X-Lead-Token`, never a URL query. A B2B customer instead uses authenticated account reads. Staff can review the saved historical snapshot, read attached private images, and mark the lead contacted (`LEADS_FRONTEND.md:334-364, 403-412`).

### Configurable and fixed form fields

Every form has exactly five ordered, server-owned fixed fields: required name, phone, governorate, and district, plus optional email. Staff cannot change their keys/order/required flags. Staff may configure 0-40 fields from `text`, `textarea`, `number`, `select`, `multiselect`, and `boolean`; each requires bilingual labels and a stable machine key, and choice fields use stable choice keys (`FORMS_FRONTEND.md:67-83, 130-142`). Form definitions have one current version per type. An edit to an active form takes effect immediately; no draft/publish-copy/history endpoint exists, and stale submissions return `FORM_CONFLICT` for user review (`FORMS_FRONTEND.md:21, 147-155, 251-259`).

The contract does not seed type-specific questions. It says the confirmed own-material requirement should be configured in the applicable questionnaire, but whether any service requires supplied material remains unresolved (`FORMS_FRONTEND.md:19`). The examples are illustrative, not approved content (`FORMS_FRONTEND.md:182-195`).

## Wholesale catalog and pouch rules

Wholesale supports both native B2B simple products and selected B2C products. Native products are B2B-only, simple, and have no variants, SKU, price, stock, cart, or checkout. Reused B2C products are explicit references and read-only projections: staff can select only active products with visible category ancestry, and B2B receives no B2C mutation permission. The projection omits price, stock, SKU, sale, currency, and retail dashboard version (`WHOLESALE_FRONTEND.md:7-15, 109-127`).

Each offer has a fixed composition. Simple/native sources use one null-variant row; B2C variant sources may mix distinct variant IDs with fixed piece counts. The server derives `piecesPerPouch`. Customers select an integer number of whole pouches; they cannot customize composition. There is no displayed/calculated price, payment, stock reservation, or stock deduction, and zero retail stock does not block an inquiry (`WHOLESALE_FRONTEND.md:13-15, 87-103, 129-145, 262-274`). Leads requires at least one wholesale row and accepts up to ten distinct offers; each requested pouch quantity is 1-10,000 (`LEADS_FRONTEND.md:103-117`).

| Leads dashboard               | B2B `superAdmin`, `admin`, or `moderator` bearer for lists/details/images/contacted (`LEADS_FRONTEND.md:13, 30-33, 352-364`)                                     | Guest tracking secrets and draft secrets must remain private, never in URL query, analytics, logs, or shared caches (`LEADS_FRONTEND.md:15`).                                              |

Auth is store-separated. Access JWTs last 15 minutes; refresh uses the browser-managed HttpOnly, store-specific cookie and must serialize concurrent refreshes. The session has a fixed seven-day lifetime that refresh does not extend. Refresh requires an allowed `Origin`; browser code must use credentials and cannot read the cookie. Login/refresh rotate cookie state; replaying the prior refresh value fails (`AUTH_FRONTEND.md:21-33, 80, 118-153, 179-184`). Signup creates only a `user` account, requires email confirmation before login, and the verification/recovery OTP is a six-digit string, single-use, expires in 10 minutes, permits five attempts, and has a 60-second resend interval. Registration, verify-email, login and password reset are separate calls; OTP delivery failure can return `EMAIL_UNAVAILABLE` (`AUTH_FRONTEND.md:39-49, 57-82, 173-192`).

B2B profile prefill is optional frontend convenience; Forms/Leads do not look up profile/address IDs, and prefilled contact remains editable (`FORMS_FRONTEND.md:142`; `USERS_FRONTEND.md:347-355`). Users exposes profile and saved-address APIs, but saved governorate is free text and has no `governorateCode`; do not infer a shipping code from its label (`USERS_FRONTEND.md:65-85, 337-341`).

## Staff notifications and email boundaries

The first successful Lead submission creates one sparse `lead.submitted` B2B staff notification in the same business transaction. All current authorized staff see the store feed, while read receipts are personal. The feed exposes only the lead resource ID, not customer/contact/answer/image details. Read acknowledgment does not mark the Lead contacted; that remains a distinct staff action (`NOTIFICATIONS_FRONTEND.md:52-60, 88-102, 148-154`; `LEADS_FRONTEND.md:430-436`). Notifications have no TTL/delete/mark-all-read endpoint and no customer/public route, email endpoint, or push route (`NOTIFICATIONS_FRONTEND.md:198-204`).

Customer email is a separate internal worker, not a frontend API. A B2B `lead.submitted` email is queued only when the submitted contact includes email and SMTP plus `B2B_TRACKING_URL_TEMPLATE` enable that side. The template token belongs in the URL fragment; browser code extracts it and sends it via `X-Lead-Token`. No frontend delivery status or resend/recovery endpoint exists. SMTP is at-least-once and can duplicate or arrive late; delivery failure does not undo a committed lead. The contract reports safe inspection found SMTP configured but both templates unset, so customer event emails were disabled at that inspection; this is configuration evidence from the packaged review and may change (`EMAIL_DELIVERY_FRONTEND.md:17-28, 35-57, 101-125, 127-141`; `LEADS_FRONTEND.md:420-428`). Auth OTP email uses its separate direct delivery path and is not disabled by the customer tracking templates (`AUTH_FRONTEND.md:9`; `EMAIL_DELIVERY_FRONTEND.md:20`).

## Decisions and implementation questions

- Which of the five forms should be public at launch, and who supplies/approves each bilingual questionnaire, required flags, help text, and choices? Until configured and active, the public form list is empty (`FORMS_FRONTEND.md:19-21`).
- Which form(s) require customers to bring their own material? Backend docs explicitly leave this unresolved; do not encode the example `material-description` as a requirement by assumption (`FORMS_FRONTEND.md:19, 182-195`).
- Which active Wholesale offers and pouch compositions are launch content? No offer or product data is seeded by this frontend contract; a B2B admin must configure them, and public browsing returns only available offers (`WHOLESALE_FRONTEND.md:15, 23-24, 262-266`).
- What is the deployed API origin and allowed frontend CORS origin? The package leaves API origin to deployment and warns that refresh requires an allowed Origin and compatible credentialed-cookie setup (`api-conventions.md:26, 51-53`; `AUTH_FRONTEND.md:29`).
- Guest and B2B-account submissions are already in the approved scope; do not reopen whether guests are allowed. The remaining implementation decision is the private client persistence strategy for one-time draft and tracking secrets, including shared-device behavior and clearing. Guests alone receive tracking credentials, whereas account-owned submissions use account reads (`LEADS_FRONTEND.md:9-13, 334-350`). There is no server recovery/renewal (`LEADS_FRONTEND.md:56-65, 258-262, 401-412`).
- Is email a launch requirement? If yes, operations must supply the B2B tracking template with the actual frontend route plus SMTP configuration. The template does not prove the route works, and live SMTP/browser delivery has not been verified (`EMAIL_DELIVERY_FRONTEND.md:35-46, 127-141`).
