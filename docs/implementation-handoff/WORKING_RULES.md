## Model orchestration and subagents

The selected main model is the planner, orchestrator, decision owner, integrator and final reviewer, whatever its model name. Respect the owner's main model and reasoning effort; do not silently change them. Optimize correctness, quality, total usage/token/compute consumption, latency, coordination cost, and reliability for the whole workflow. Delegation is a tool, not a requirement.

### Decide whether to delegate

Do not delegate by default. Work directly when the main model already has the context and can finish with equal or better quality at lower total cost. Do not delegate trivial reads, status checks, small obvious edits, tightly coupled fragments, or passive waiting. Do not create agents to appear busy. Consider context transfer, repeated reading, independence, time saved, review/integration effort, conflict risk, and likely total consumption.

Use a bounded subagent when the task is independent and reliable with little context transfer, or independent verification materially improves safety. Normally use one implementer, not multiple agents doing the same task. Do not explain routine delegation decisions; explain meaningful tradeoffs or escalation.

### Model and effort selection

- Prefer the actual available newest capable low-cost model. Luna 6 is preferred for bounded discovery, research, routine implementation, tests, documentation, debugging and moderate verification when reliable.
- Use Sol 6.1 for genuine complexity, subtle integration, architecture/security/concurrency reasoning or when a substantive Luna result shows more capability is needed. If Sol 6.1 is already the main model, direct work can be cheaper than another Sol.
- Terra 5.6 is only a legacy fallback when concrete evidence makes it preferable to Luna for the specific task. Do not use it merely as a historical middle tier.
- Astra is an exceptional last resort, not a default planner, implementer, reviewer, security checker, second opinion, or verifier. Important/critical work does not justify Astra.
- Before considering Astra, inspect a substantive Sol 6.1 attempt and distinguish a real reasoning limit from missing context, unclear requirements, permissions, tools, installation or runtime failures. Fix context/specification first. Allow at most one justified corrective Sol attempt, not retries to manufacture eligibility. Tool/environment failures never justify Astra.
- Before dispatching Astra, explain exactly what Sol tried and could not resolve, why the remaining issue needs more reasoning, and the precise bounded task. Obtain the owner's explicit approval for that task. General delegation approval is insufficient. Send only necessary context, not the entire project/history.

On failure, inspect the output and identify scope/context/tool/environment/capability cause. Correct context first; finish directly when now efficient. Stop repeated, stalled, abnormal-consumption or runaway loops, explain the real issue and recover directly where feasible.

Prefer bounded event-driven waits; a timeout alone does not prove failure. Continue independent useful work while waiting.
