## Build and regeneration procedure

1. Confirm approved content and the actual public website origin for each store. Configure `VITE_DATA_MODE=live`, the approved `VITE_API_ORIGIN`, and that store's real `VITE_SITE_ORIGIN` using the deployment's environment management. Never put passwords or provider secrets in frontend environment variables. Do not use the temporary API origin as either website's canonical domain.
2. In each app directory, run `npm run lint`, `npm run format:check` and `npm run build`. Run the relevant shared tests from the project root. Use `build:review` only for fixture review; review builds remain non-indexable. `--mode integration` is local testing only and enables a loopback API proxy; do not deploy that mode.
3. The normal build writes that app's `dist/`. Its `routes.json` maps clean public URLs to named HTML files, defines ID/alias redirects and identifies the private/dynamic app shell. Do not publish `.prerender/` as a separate application server.
4. At the final website host, apply the generated rewrites and **real HTTP 308** redirect rules. Preserve query strings; redirects must point directly to the latest same-language canonical URL. Configure real 404 behavior for unknown/unavailable public content. The Vite preview verifies local behavior only and does not configure the VPS.
5. Upload/publish the complete matching build atomically through the approved deployment process. Regenerate when product/offer names or details, slugs, publication/availability, guides, homepage settings, contacts or SEO defaults change. Invalidate stale public HTML and old route rules; keep historical aliases. Live dashboard saves alone do not regenerate already-hosted static files.
6. Check delivered HTML with JavaScript disabled, localized titles/descriptions, one canonical per page, reciprocal EN/AR alternates, structured-data parsing, images/fonts, the generated sitemap and robots. Keep private and placeholder pages out of the sitemap. Confirm all indexable URLs return meaningful content with HTTP 200 and retired aliases return 308.
7. Verify representative public and signed-in journeys on the actual HTTPS website origins before owner release acceptance. Preserve any test records or pending acceptance limits in the handoff instead of claiming them complete.

An isolated Phase 8 metadata check uses reserved `b2c.example.test` and `b2b.example.test` origins under `output/phase8/*-metadata/`. These are test artifacts only. They must not be copied as production configuration or deployed. Its 32 current empty-catalog pages passed canonical, language, placeholder exclusion, sitemap and JSON-LD parsing checks; this does not verify final domains or a populated production catalog.

## Monthly review

- Review new/changed products and service content with the owner. Check both languages, spelling, specifications, useful headings, internal links, image crops and descriptive alt text. Update existing templates rather than creating unsupported features.
- Crawl the current indexable URLs and sitemap. Check broken links/images, status codes, redirects, canonical/alternate consistency, duplicate/empty titles, accidental noindex, private pages and stale unavailable products/offers.
- Validate Product, Organization and Service JSON-LD against visible, approved content. Do not add fabricated reviews, business facts, ratings or commercial claims. Structured data does not guarantee a rich result or AI citation.
- Review Search Console/Bing indexing and search performance once the owner supplies domains and approved access. Record the reporting period, meaningful changes, pages affected and recommended next actions. No verification token or account has been invented or installed.
- Check actual field performance when available, plus representative mobile navigation, forms, Arabic typography and layout stability. Local warm-browser measurements are diagnostic evidence, not a substitute for real-user data.
- After approved changes, rebuild, publish through the authorized workflow, check actual delivered pages and keep a dated record of the build, affected URLs and validation. Deployment approval remains separate from editing content.

Search verification meta tags can be added to the appropriate app's `index.html` after the owner provides an approved token; DNS verification belongs to the domain operator. Any analytics integration requires a confirmed tool, property ID and privacy/content decision before implementation. No monthly automation or external-account access is created by this document.
